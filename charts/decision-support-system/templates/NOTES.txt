If the pods crashloop before serving, check these in order - the first two are
startup failures the service raises deliberately, and log the real cause
before exiting:
  1. "AZURE_OPENAI_ENDPOINT and AZURE_OPENAI_API_KEY" in the crash log means a
     models.* value uses azure: but azureOpenai.* was left unset - this chart
     should have caught it at render time (see _helpers.tpl), so seeing it at
     runtime instead means values were set through some other path (--set,
     a second -f) that bypassed the guard.
  2. "the network is configured but no schema packs loaded" means
     network.discoveryBaseUrl/invocationBaseUrl are set, the schema-pack
     emptyDir came up empty, AND the pod's own GitHub fetch on boot also found
     nothing at schemaPacks.ref - check the ref is real
     (network-specs@schema-packs-v0.1 as of this chart's writing, not `main`)
     and that the pod has egress to api.github.com.
  3. A key in `envConfig` matching no Settings field is silently ignored, NOT
     a boot failure - Settings uses extra="ignore" precisely so a real
     deployment's non-DSS_ vars (OPENAI_API_KEY, the Langfuse OTEL_* keys)
     don't raise. A typo'd DSS_* key in envConfig therefore looks like it took
     effect and quietly did not; there is no render-time or boot-time check
     for this, unlike the guards this chart adds for models.*/network.*.
